# CozyCrazyCraft Quest System 0.4.1 — QA / Regression / Performance Hardening Report

Branch: `quest-qa-regression-0.4.1`  
Base: `2e413cba282af6a11d5372b177d6c51d9df4503b`  
Scope: tests, validators, instrumentation, reproducible defects, low-conflict hardening.

This branch intentionally does **not** rewrite `VillageConversationQuestManager`, `QuestHintNetwork`,
`NamedPlaceBridge`, `StructureSurveyCompletionBridge`, or `RecoveryQuestRuntime`. The integration branch
owns those behavior changes. The QA branch supplies executable guardrails and a precise defect/acceptance map.

## 1. Watchdog finding: separate two different causes

The September 7 playtest log contains multiple ModernFix watchdog reports. They are not one homogeneous
"quest lag" event.

### Unrelated teleport/chunk stalls

At `11:21:47`, the watchdog reports `40001 ms`. The actual **Server thread** is blocked in
`ServerChunkCache.getChunkBlocking` under `TeleportCommand`. The same signature appears again at
`11:55:20` (`40001 ms`). These are teleport/chunk-load stalls and should not be attributed to quest lookup.

### Quest-owned structure-locate stall

A different incident begins at `11:24:10` (`40029 ms`) during an ordinary villager interaction. The actual
**Server thread** stack contains:

`VillageConversationQuestManager.onEntityInteract`
→ `selectOffer`
→ `prepareTarget`
→ `resolveStructureTarget`
→ `NearbyStructureResolver.findNearest`
→ vanilla `ChunkGenerator.findNearestMapStructure` / Structure Gel `GridStructurePlacement.findNearest`
→ structure checks / generation work.

ModernFix then reports the same blocked tick repeatedly at approximately 41-second intervals with cumulative
elapsed values `81.698s`, `122.968s`, `163.683s`, `205.344s`, `246.666s`, `287.273s`, `328.467s`,
`369.254s`, `411.004s`, `452.317s`, `493.425s`, and finally `534.317s`.

That is strong evidence for one **quest-triggered synchronous structure locate that kept the integrated server
blocked for roughly nine minutes**, not merely a nearby unrelated chunk-generation hiccup. The stack ownership
matters: the player interaction is the caller, and Structure Gel/structure checking is the expensive callee.

`tools/analyze_watchdog_log.py` now classifies incidents from the actual Server-thread dump so future triage
does not confuse these two classes.

## 2. Performance diagnosis

`NearbyStructureResolver` has a single expensive boundary: `findNearestMapStructure(...)`. The normal authored
offer path reaches it synchronously from `onEntityInteract` on a target-cache miss.

There is already useful caching in `VillageConversationQuestManager`:

- key: `seed : village_key : quest_definition_id`;
- current lifetime: `6000` ticks;
- null results are cached too.

However, `data/targeting_policy.json` specifies `24000` ticks for positive structure results and `6000` for
negative results. The current single TTL therefore expires valid positive targets four times sooner than policy.
More importantly, the first miss still happens on the server thread while the player is right-clicking a villager.

There is also a retry fan-out path: if a mixed-family locate returns an illegal nearest member, the manager retries
each candidate structure ID individually. For a definition with N candidates, one click can therefore become
1 + N expensive locator calls before the cache fills.

### Integration recommendation

Do not "fix" this by calling the locator from a tick loop. Keep the expensive boundary explicit and cached.

Preferred target-cache key:

`dimension + world_seed + village_or_regional_cell + normalized_target_family + tier/macro policy`

Recommended lifetimes:

- positive generated target: at least the policy `24000` ticks;
- negative/not-found: policy `6000` ticks;
- exact accepted contract target: persist in player/village quest state and do not re-locate it.

Avoid repeated per-definition locates when several definitions ask for the same structure family. Resolve a
normalized target family once per village/cell and let quest definitions filter/scoring operate on cached
candidates. If a broad Structure Gel locate can still take seconds, move resolution away from the click-critical
path: e.g. village/board preparation with bounded work, or an explicit "checking maps" operation that does not
hold the server tick hostage. Never perform broad locate work every ordinary interaction.

`NearbyStructureResolver` now emits one warning for any locate taking at least 250 ms, including thread, origin,
radius, candidate IDs and result. This is diagnostic only; it changes no target-selection semantics.

## 3. P0 defects

### P0-STRUCT-1 — Surface survey can still complete from horizontal locator radius

`VillageConversationQuestManager.onPlayerTick` skips the radius fallback only for `UNDERGROUND` and
`SUBMERGED`. A surface `STRUCTURE_SURVEY` can still set `objective_complete` when X/Z distance to the locator
falls inside `target_radius`, even if the player is outside the generated structure.

**Repro:** accept a surface survey, stay outside the visible/generated structure, cross only the configured
horizontal target radius, wait one second.

**Patch direction:** remove structure-survey completion from the generic local radius path. Structure surveys
should be completed only by the structure-discovery bridge using meaningful structure presence/dwell.

### P0-STRUCT-2 — Exact occupancy is whole-StructureStart bounding-box occupancy

`NamedPlaceBridge.insideExactStructure` verifies the expected start chunk, which correctly rejects the wrong
instance, but it uses `current.getBoundingBox().isInside(playerPos)` as the spatial proof. Large multi-piece
structures can contain large empty volumes inside the whole-start box.

**Patch direction:** once the exact `StructureStart` is identified, require the player to be inside at least one
real structure piece bounding box. Add a short dwell (for example 10–20 ticks of stable qualifying presence)
before CONFIRMED. Keep full XYZ checks. Do not substitute center/radius proximity.

### P0-REC-1 — Recovery evidence is still created by occupancy

`StructureSurveyCompletionBridge` creates `RecoveredEvidence` and immediately marks the objective complete
as soon as `insideExactStructure(...)` succeeds. This is exactly the field-test fiction failure: the backend
creates an item instead of the player finding/interacting with the object.

**Patch direction:** bind evidence to a real eligible container in the exact assigned instance, or to a deliberate
quest cache/interactable. The physical interaction should atomically grant/bind the evidence and advance the
objective. Do not silently inventory-mint from presence.

The existing evidence matcher itself is good: it requires the exact `RECOVERED_EVIDENCE` item plus quest ID,
village key and target key. A similarly renamed item is not accepted, and successful turn-in shrinks one matching
item.

### P0-REC-2 — Physical proof items and recovery evidence are currently two different truths

`ProofLootInjector` injects distinctive proof items such as `stablemasters_seal`, while the authored recovery
runtime accepts the generic tagged `recovered_evidence` item created by occupancy. A player can therefore find
a convincing named chest object that is not what the recovery turn-in consumes.

**Patch direction:** one quest must have one player-visible evidence truth. Either bind the injected physical item
to the active contract (including quest/village/instance identity) or remove it from that recovery fiction.

### P0-PERF-1 — Villager click can synchronously enter a pathological Structure Gel locate

Confirmed by the `11:24:10`–`11:32:24` server-thread dumps described above.

**Patch direction:** cache normalized target families at village/cell scope, honor separate positive/negative TTLs,
avoid N+1 candidate retries, and take expensive initial resolution off the ordinary click-critical path.

### P0-UI-1 — NPC directions/prose still emitted through action bar

`QuestHintNetwork.giveLead` constructs multi-sentence underground guidance and sends it with
`displayClientMessage(..., true)`. Gore rumor/lead text and survey/recovery return instructions also use the
action bar.

**Patch direction:** speech/directions/referrals belong in Conversations. Action bar is limited to short transient
state changes such as `Survey complete: Amber Rest.` or `Stable Ledger recovered.`

### P0-NAV-1 — Gore KNOWN marker is still the structure locator/center, not a safe approach

`GoreTunnelLead.revealSpecialistLead` calls `NamedPlaceBridge.revealStructureToAtlas` with the raw located
target and then describes it as a surface reference. That label does not make the marker safer.

**Patch direction:** store an explicit `approach_pos` separate from objective/identity. Prefer verified entrance;
otherwise use nearest safe structure edge toward issuing village. Atlas reveal uses `approach_pos`; structure
identity/completion continues using exact start/piece evidence.

### P0-NAV-2 — Gore discovery retains broad fallback

When exact occupancy fails, Gore can still confirm within `104` horizontal blocks and `80` vertical blocks of
the locator. This can promote KNOWN/LEAD to CONFIRMED before meaningful tunnel discovery.

**Patch direction:** legacy saves may receive a compatibility migration, but current contracts should not use
this fallback. Require exact assigned start + qualifying piece/dwell or a bespoke verified Gore tunnel signal.

## 4. P1 defects

### P1-PERF-1 — Positive target cache TTL is below policy

Runtime: `6000` ticks for both found and not-found. Policy: `24000` positive, `6000` negative.

### P1-SOC-1 — Close unnamed villages can collide in fallback identity

When no persistent village name is available, `VillageContext` uses a 128-block quantized fallback key. Two
unusually close/adjacent settlements can land in the same fallback cell and share actives/hints/standing.

**Patch direction:** use the resolved meeting POI/settlement anchor identity (or a persistent civic UUID/start
identity) rather than only coarse coordinate quantization. Keep name as display data, not sole identity.

### P1-SOC-2 — Profession death/jobless-village recovery remains integration-owned

Quest offers are still selected from actual villager trade professions. The field-playtest requirement for civic
roles/successors is not implemented on this base. Tests in the regression matrix explicitly cover:
jobless village, tiny village, all eligible profession holders dead, wrong-villager clicks and close-village
cross-routing.

### P1-VAR-1 — No recent structure-instance history in authored offer selection

`selectOffer` checks whether a quest definition is completed, but does not down-weight the just-used target
instance when a different definition can resolve to the same structure.

### P1-VAR-2 — No recent primary reward-archetype history

There is no player/village chapter history preventing saddle→saddle or equivalent primary reward repetition.

### P1-CONVO-1 — Hint variation has no recent-variant suppression

Profession and deterministic UUID/quest rolls create some variety, but there is no small recent line/semantic
variant history to prevent repeated identical-feeling hints across several villagers.

## 5. P2 / static content observations

- Conversations now receive a hard QA ceiling of 45 words per NPC beat and warnings above 30 words. The
  Conversation Bible's normal target remains much shorter; the hard ceiling is intentionally not used as a
  writing target.
- Authored `_offer` stems are checked for active/turn-in state coverage and incomplete triplets are surfaced.
- The regression matrix includes the Bible rule that a visible pool should not exceed two quests with the same
  core verb; this remains a manual/content-selection assertion until the runtime exposes a normalized verb field.

`NearbyStructureResolver`
: slow-locate instrumentation at the shared expensive boundary, warning at 250 ms.

## 7. Integration instructions

1. Cherry-pick the QA/validator commits early. They are designed to stay green while printing the current P0/P1 debt.
2. Cherry-pick the isolated `NearbyStructureResolver` instrumentation commit independently; it changes no
   completion/navigation semantics.
3. As each integration-owned P0 is fixed, run `python tools/validate_qa_regression_contracts.py` and manually
   execute the corresponding matrix cases. The `KNOWN DEBT` line for that behavior should disappear.
4. Run `python tools/analyze_watchdog_log.py <latest.log>` after a fresh new-village interaction test. Any
   `QUEST_STRUCTURE_LOCATE` report over 250 ms should be correlated with the new resolver timing line.
5. For structure completion, do not accept a patch that merely shrinks a radius. The acceptance condition is
   exact assigned instance + meaningful piece/discovery signal + XYZ correctness; underground must never
   confirm from surface X/Z.
6. For recovery, do not accept a patch that simply renames the auto-created evidence. The player must physically
   interact with the evidence source, and the object turned in must be the object the player believes they found.
7. For navigation, keep `RUMOR` non-exact. `KNOWN` may mark only a fictionally justified destination/approach;
   underground/Gore markers require a separate safe approach coordinate.
8. Before 0.4.1 is called playable, execute every P0 row in `data/qa_regression_matrix.json`, then P1 social and
   variety rows. Leave `KNOWN_DEBT` only for deliberately deferred P2 work; no P0 debt should remain.
